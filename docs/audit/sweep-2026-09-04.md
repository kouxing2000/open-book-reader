## A4-1 · P2 · CONFIRMED — a div-paragraph article loses the toolbar icon's auto-pick

`OBR._proseStats` (`settings.js`) counts leaf `p`, `blockquote` and `li` blocks and nothing
else. An article whose body copy sits in `<div>`s — older CMS templates, hand-rolled sites,
and `paulgraham.com`, which is `<font>` inside tables — therefore reports **zero** prose words
while a reader sees a long article. Measured live: `paulgraham.com/greatwork.html` extracts
**11,619 words** and `_proseStats().words === 0`.

That number feeds the toolbar icon's auto-pick, which opens the gallery when
`_imageCount() >= autoGalleryMin` **and** `_articleWordCount() < autoTextMinWords`. With the
prose count stuck at 0, the second half is always true, so **an image-bearing article of this
shape opens in gallery mode**. CLAUDE.md claimed "a substantial article always wins"; it wins
only if its paragraphs are paragraphs. That sentence is now corrected.

Reproduced, not inferred: `tests/fixtures/div-paragraph-article.html` (4 div paragraphs, 12
canvas-PNG images) plus a test asserting `_proseStats().words === 0`, `_countWords(body) > 200`,
and `_autoToggle() === 'images'`. The test pins the CONSEQUENCE, so changing the rule changes
the test — it documents a known limit rather than blessing it.

The same count gates the auto-open sentinel's ladder, so a rule in `auto` mode on such a site
inherits the same blindness. Not separately reproduced.

Fix options, cheapest first: count `<div>` leaf blocks that contain no block children and clear
`MIN_PARA_WORDS`; or fall back to `_countWords(document.body.textContent)` when the prose total
is 0 and the body is long. Both widen a heuristic that currently has a clean false-positive
record, so this wants a decision, not a reflex.

## A4-2 · P3 · CONFIRMED — the "extraction looks wrong" nag fires on correct extractions

`_wholeExtractionSuspect` returns true when the page holds ≥200 prose words and the extraction
kept under half of them, and it gates a user-facing nag toward the ⌖ Pick button
(`reader.js:2269`). Asked for the **engine's own verdict** rather than a lookalike ratio, it
fires on **2 of 42** rows — both Ars Technica, both ratio 0.49, and both extractions are
complete and correct when read by hand.

Cause is the one the code comment already predicts: Ars pages carry comments and article
teasers, Readability strips them, `proseWordCount` counts them, so `kept/live` sinks on a
perfect read. The comment calls this acceptable. What was missing was a rate — on a top-tier
tech news site it is not rare, it is **every article**.

Not fixed. It is a non-blocking hint, and tightening the ratio trades these false positives for
false negatives on the truncation cases the nag exists to catch. Logged so the next person has
the number.

## A4-3 · Info · FIXED — the manual site proxy had no `chrome.i18n` shim

`tests/manual-site-proxy.mjs` shimmed `chrome.storage` but not `chrome.i18n`, so `OBR.t()`
echoed raw keys and the overlay rendered `colophonTheEnd`, `colophonRate`, `colophonFeedback`
as visible text. It polluted every measurement taken off the overlay and would mislead anyone
using the proxy by hand. Now fed from the real `_locales/en` catalogue. CLAUDE.md already
warned about this exact failure for the capture harness — the proxy was the copy that never
got it.

## A4-4 · Info · method — a site list rots, and a 404 page extracts beautifully

On the first run **11 of 42 URLs were dead or bot-walled**, and the grader scored several of
them PASS: a 404 page is a valid HTML page with a nav bar, so it extracts "successfully". A
grade computed from a page the target site never served is worse than no grade.

`scripts/sweep-sites.mjs` now classifies `DEADURL` / `BOTWALL` from the page's own `<title>`
**before** any scoring (most sites serve a 404 body with HTTP 200, so the status code cannot be
trusted), including non-English 404 titles. The dead URLs were replaced with ones scraped from
live front pages rather than guessed a second time.

Also corrected in the runner: the reader's own colophon was being counted as extracted article
text, adding ~10 words of our UI to every row; and link density was briefly a failing grade
until Wikipedia — a textbook-clean extraction — scored ~9 links per 100 words and proved the
metric manufactures failures. Link density is now reported, never graded.

## A4-5 · Info — MDN renders interactive-example source as body text

`developer.mozilla.org` scored WIDE (ratio 2.54). By hand: the extracted body opens with
`Try it <section id="default-example"> <p id="example-element"> London. Michaelmas term…` —
MDN's live-example markup, which the page carries as text. Faithful rendering of MDN's own
document; noise rather than a defect. No action.

## What the sweep did not cover

The proxy strips scripts to freeze the SSR DOM, so lazy hydration, infinite scroll and
client-side routing are out of scope here (the Playwright suite covers them against fixtures).
Four SNAPSHOT and four BOTWALL rows produced no signal about extraction at all. Nothing was
verified in a real browser with the real extension installed.
